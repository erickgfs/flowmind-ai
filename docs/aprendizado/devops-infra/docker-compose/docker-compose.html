Docker Compose, do zero

Um único arquivo descreve o banco e o cache do FlowMind AI. Um comando liga os dois, com os dados guardados fora dos containers e uma checagem que diz quando cada serviço está pronto de verdade.

Antes de começar

  • Aulas 1 a 3: imagem, container, porta e volume (Docker), e os dois programas que vamos ligar (PostgreSQL e Redis).
  • Variável de ambiente: um par NOME=valor que um programa lê ao iniciar, para se configurar sem mudar o código. Ex.: POSTGRES_PASSWORD=abc123 diz ao PostgreSQL qual senha usar.
  • YAML: o formato do arquivo. Três regras bastam:

O problema e a ideia

O problema

Comandos enormes, toda vez

Só com o Docker, ligar o banco e o cache exige digitar dois docker run cheios de opções (veja abaixo). É fácil errar uma letra ou digitar diferente do colega.

O Docker Compose deixa você escrever tudo uma vez num arquivo, o docker-compose.yml, e ligar tudo com docker compose up -d. O arquivo vira a documentação de "do que este projeto precisa para rodar".

Analogia

A partitura do maestro

  • Sem Compose: você explica a cada músico o que tocar, um por um, toda vez.
  • Com Compose: você escreve a partitura (o YAML) e entrega ao maestro (o comando docker compose).
  • O maestro coordena todos os músicos (containers): quem entra, em que porta, com quais instrumentos (volumes).

Onde a analogia falha: o maestro liga todos ao mesmo tempo. Para um esperar o outro, é preciso dizer explicitamente com depends_on.

sem Composetoda vez, à mão
docker volume create postgres_data
docker run -d --name flowmind-postgres \
  --restart unless-stopped \
  -e POSTGRES_USER=flowmind \
  -e POSTGRES_PASSWORD=... \
  -e POSTGRES_DB=flowmind \
  -p 5432:5432 \
  -v postgres_data:/var/lib/postgresql/data \
  postgres:16-alpine

docker volume create redis_data
docker run -d --name flowmind-redis \
  --restart unless-stopped \
  -p 6379:6379 -v redis_data:/data \
  redis:7-alpine \
  redis-server --appendonly yes --requirepass ...
com Composeescrito uma vez no YAML
docker compose up -d

# o que acontece, em ordem:
# 1. lê o .env e troca cada ${...} do YAML
# 2. cria a rede flowmind-ai_default
# 3. cria os volumes (se não existirem)
# 4. baixa as imagens (se não estiverem no PC)
# 5. cria e liga os dois containers
# 6. começa os healthchecks:
#    em ~10s, os dois ficam (healthy)

Quem fala com quem

"Rodando" não é "pronto"

Regra prática: containers e rede são descartáveis e o Compose recria tudo a partir do YAML. Só os volumes guardam o que você não consegue recriar. Por isso o -v pede atenção dobrada.

O arquivo, linha por linha

flowmind-ai/docker-compose.ymlversão em uso no projeto
name: flowmind-ai                 # prefixo da rede e dos volumes (flowmind-ai_default...)

services:
  postgres:                         # nome do serviço = hostname dentro da rede
    image: postgres:16-alpine       # major 16 travada; patches (16.x) entram com "pull"
    container_name: flowmind-postgres # nome fixo, facilita "docker exec"
    restart: unless-stopped         # volta sozinho, exceto se você parou
    environment:
      POSTGRES_USER: ${POSTGRES_USER}         # o Compose lê do .env
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD} # só vale na 1ª inicialização do volume!
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "${POSTGRES_PORT:-5432}:5432"     # host:container; 5432 é o padrão se faltar no .env
    volumes:
      - postgres_data:/var/lib/postgresql/data  # volume nomeado → dados persistem
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 10s                   # testa a cada 10s
      timeout: 5s                     # mais que isso conta como falha
      retries: 5                      # 5 falhas seguidas → unhealthy

  redis:
    image: redis:7-alpine
    container_name: flowmind-redis
    restart: unless-stopped
    command: ["redis-server",
              "--appendonly", "yes",                 # AOF: cada escrita vai pro disco
              "--requirepass", "${REDIS_PASSWORD}"]   # sem senha = qualquer um na porta entra
    ports:
      - "${REDIS_PORT:-6379}:6379"
    volumes:
      - redis_data:/data                 # onde fica o appendonly.aof
    healthcheck:
      # $$ = "não resolva agora": o shell DENTRO do container é quem lê $REDIS_PASSWORD
      test: ["CMD-SHELL", "redis-cli -a \"$$REDIS_PASSWORD\" --no-auth-warning ping | grep PONG"]
      interval: 10s
      timeout: 5s
      retries: 5
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD}   # expõe a senha ao healthcheck acima

volumes:                              # declara os volumes nomeados usados acima
  postgres_data:
  redis_data:

Glossário

Docker Compose
Ferramenta que liga vários containers a partir de um arquivo.
docker-compose.yml
O arquivo, em YAML, que descreve os containers do projeto.
Serviço
Cada item dentro de services:. Vira um container.
Variável de ambiente
Configuração NOME=valor que o programa lê ao iniciar.
.env
Arquivo com as variáveis do projeto, incluindo senhas. Fica fora do Git.
.env.example
Modelo do .env com valores falsos. Vai para o Git.
Interpolação
Trocar ${NOME} no YAML pelo valor do .env.
Rede
Ligação interna onde os containers se acham pelo nome do serviço.
Volume nomeado
Volume com nome (postgres_data) onde os dados persistem.
Healthcheck
Teste periódico que diz se o serviço está pronto, e não só ligado.
Restart policy
Regra de quando religar um container que parou.
-d (detached)
Rodar em segundo plano e devolver o terminal.

Experimente: os dados sobrevivem?

Troque SENHA pelo valor de REDIS_PASSWORD no .env. Rode tudo dentro da pasta flowmind-ai/.

  1. Veja o estado atual

    docker compose ps

    Esperado: os dois serviços Up ... (healthy).

  2. Guarde um valor no Redis

    docker exec flowmind-redis redis-cli -a SENHA --no-auth-warning SET prova:volume "sobrevivi"

    Esperado: OK.

  3. Apague containers e rede

    docker compose down
docker ps -a

    Esperado: nenhum container flowmind-* na lista.

  4. Ligue de novo e leia o valor

    docker compose up -d
docker exec flowmind-redis redis-cli -a SENHA --no-auth-warning GET prova:volume

    Esperado: "sobrevivi". Containers novos, mesmo volume.

  5. Veja o YAML com as variáveis trocadas

    docker compose config   # mostra as senhas: não compartilhe a saída

    ${POSTGRES_USER} aparece como flowmind.

  6. Desfaça o teste

    docker exec flowmind-redis redis-cli -a SENHA --no-auth-warning DEL prova:volume

Teste seu entendimento

1. O que o Compose faz que o Docker sozinho não faz?

Lê um arquivo com a descrição de vários containers e liga, desliga ou apaga todos juntos com um comando, sempre do mesmo jeito.

2. Depois de docker compose down, o banco foi apagado?

Não. down apaga containers e rede, mas mantém os volumes. Só down -v apaga os volumes.

3. Por que o .env não vai para o Git e o .env.example vai?

O .env tem as senhas reais. O .env.example mostra quais variáveis existem, com valores falsos.

4. Uma API em outro container do mesmo Compose conecta em localhost:5432 ou postgres:5432?

Em postgres:5432. Dentro de um container, localhost é ele mesmo.

5. O container está "Up", mas não "healthy". A API já pode conectar?

Não é garantido. "Up" só diz que o processo ligou; "healthy" diz que o teste de prontidão passou.
