O problema e a ideia

O problema

flowmind-final-agora-vai-2

  • Você muda o login, quebra tudo e não lembra como estava ontem.
  • "Cópias de segurança" viram pastas com nomes cada vez piores.
  • O notebook estraga e o projeto vai junto.
  • O recrutador vê o resultado, mas não como você chegou nele.

O Git tira fotos (commits) do projeto quando você manda e deixa voltar a qualquer uma. O .gitignore diz o que fica de fora; o Conventional Commits padroniza as legendas.

Analogia

O álbum de fotos da reforma

  • Commit = foto datada com legenda: "instalei a elétrica da cozinha".
  • Staging = o enquadramento: você escolhe o que aparece antes de clicar.
  • .gitignore = "não fotografe o cofre (senhas) nem o lixo (o que dá para refazer)".
  • Conventional Commits = toda legenda começa pelo tipo de serviço, para achar rápido.

Onde a analogia falha: uma foto real guarda a casa inteira de novo. O Git guarda uma cópia só de cada arquivo que não mudou, e as fotos apontam para ela.

# qual regra ignora um arquivo?
git check-ignore -v .env

Regra prática: ignore o que é segredo ou o que dá para recriar com um comando. O package-lock.json entra: é a receita que recria as mesmas versões em outra máquina.

Glossário

Git
Programa que guarda o histórico de mudanças e deixa voltar a qualquer ponto.
Repositório
Pasta controlada pelo Git; o histórico fica em .git.
Pasta de trabalho
Os arquivos como estão agora, do jeito que você edita.
Staging (index)
Onde você monta o próximo commit com git add.
Commit
Foto do projeto com mensagem, autor, data e um hash.
Hash
Código único do commit, como d0eca83.
Branch
Linha do histórico com nome; a principal é main.
Untracked
Arquivo que o Git vê, mas ainda não versiona (??).
.gitignore
Padrões de nomes que o Git deve ignorar.
Conventional Commits
Padrão tipo(escopo): descrição.
Remoto
Cópia do repositório num servidor (GitHub), recebe git push.
LF / CRLF
Fim de linha Linux/macOS × Windows; os avisos são só lembretes.
Blob
O conteúdo de um arquivo guardado dentro do Git.

Experimente numa pasta de treino

Fora do projeto, para não mexer no histórico real do FlowMind.

  1. Crie o repositório de treino

    mkdir ~/treino-git && cd ~/treino-git
git init -b main

    Esperado: Initialized empty Git repository

  2. Crie um segredo e um arquivo normal

    echo "SENHA=123" > .env
echo "# Meu treino" > README.md
git status --short

    Esperado: ?? .env e ?? README.md. O segredo está prestes a vazar.

  3. Proteja o segredo

    echo ".env" > .gitignore
git status --short --ignored

    Esperado: !! .env, e .gitignore/README.md como ??.

  4. Dois commits, um assunto cada

    git add .gitignore && git commit -m "chore: ignora arquivos .env"
git add README.md  && git commit -m "docs: adiciona README"
git log --oneline

    Esperado: 2 commits, o mais novo em cima.

  5. Staging diferente da pasta

    echo "linha nova" >> README.md && git add README.md
echo "outra linha" >> README.md
git status --short

    Esperado: MM README.md. Compare git diff --cached com git diff.

  6. Prove que o .gitignore não protege o passado

    git add -f .env && git commit -m "chore: oops"
git show HEAD:.env

    Esperado: SENHA=123. A senha está no histórico, mesmo com o .gitignore.

  7. Desfaça

    cd ~ && rm -rf ~/treino-git

    Num projeto real, segredo commitado deve ser trocado.

Teste seu entendimento

1. O que são commit, staging e .gitignore na reforma?

Foto com legenda; o enquadramento antes de clicar; a regra "não fotografe o cofre nem o lixo".

2. Por que node_modules fica fora, mas package-lock.json entra?

node_modules é recriado pelo npm install; o lock é a receita que garante as mesmas versões em outra máquina.

3. Por que !.env.example vem depois de .env.*?

A última regra que combina é a que vale; o ! devolve o modelo sem segredos ao Git.

4. Classifique: rota nova, correção do 500, atualização de aula.

feat(api), fix(api) e docs.

5. Ignorar um arquivo depois de commitá-lo protege a senha?

Não. O commit antigo ainda guarda a senha; é preciso trocá-la.
