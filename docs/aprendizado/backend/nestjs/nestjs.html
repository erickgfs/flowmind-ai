Antes de começar

  • Aula 5 (Node.js, npm e TypeScript): o Nest roda no Node e é escrito em TypeScript.
  • API em poucas linhas: programa que espera pedidos pela rede e devolve respostas. Cada pedido tem um método (GET buscar, POST criar, PATCH alterar, DELETE apagar) e uma rota (/tasks). A resposta costuma ser JSON.

O problema e a ideia

O problema

Uma API que cresce sem regras

  • Rotas de usuários, tarefas, documentos, login, IA... cada arquivo fazendo de tudo.
  • Um arquivo muda e outro quebra.
  • Cada peça monta sozinha a conexão com o banco e a configuração, repetindo código.

O NestJS diz onde cada coisa fica (module, controller, service) e entrega as peças prontas a quem pede.

Analogia

O restaurante

  • Controller = garçom: anota o pedido e leva o prato. Não cozinha.
  • Service = cozinheiro: sabe a receita.
  • Module = praça da cozinha (confeitaria, grelhados).
  • Injeção de dependências = gerente: o cozinheiro pede uma panela e o gerente entrega a panela compartilhada.

Onde a analogia falha: um garçom atende uma mesa por vez. O mesmo controller atende milhares de pedidos ao mesmo tempo, graças ao event loop.

Uma rota GET /stats que conta usuários e tarefas usando o PrismaService injetado.

  1. Suba o banco e a API

    docker compose up -d     # na raiz flowmind-ai/
cd apps/api
npm run start:dev

    Esperado: Nest application successfully started.

  2. Adicione a rota em src/app.controller.ts

    import { PrismaService } from './prisma/prisma.service.js';

constructor(
  private readonly appService: AppService,
  private readonly prisma: PrismaService, // injetado
) {}

@Get('stats')
async stats() {
  return {
    users: await this.prisma.user.count(),
    tasks: await this.prisma.task.count(),
  };
}

  3. Abra http://localhost:3000/stats

    Esperado: {"users":0,"tasks":0}

  4. Provoque o erro de DI

    Tire o PrismaModule dos imports do app.module.ts e salve.

    Esperado: Nest can't resolve dependencies of the AppController (AppService, ?). Coloque de volta.

  5. Desfaça

    Remova a rota e o PrismaService do constructor, ou mantenha se quiser usá-la.

NestJS no mundo real

Na maioria das empresas, "backend em NestJS" quer dizer uma API REST: HTTP, JSON e um banco como o PostgreSQL. Só que o Nest não é um framework "de REST". Ele organiza o backend por dentro, com modules, services e injeção de dependências. REST é só uma das portas de entrada possíveis.

A ideia que vale levar: a lógica de negócio fica nos services, e o mesmo service pode ser chamado por portas diferentes.

PortaPacoteQuando se usaExemplo no FlowMind
REST@nestjs/commonO padrão. Front-end web, app mobile e integrações chamando rotas HTTPPOST /tasks cria uma tarefa
GraphQL@nestjs/graphqlFront-end com muitas telas que precisam de dados em formatos diferentes; o cliente escolhe os camposUma query traz tarefa + autor + documentos de uma vez
WebSocket@nestjs/websocketsTempo real: chat, notificações, edição colaborativaAviso na tela quando a IA termina de processar

Filas@nestjs/bullmqTrabalho demorado que não pode travar a resposta: e-mails, PDFs, chamadas de IAResumir um documento com IA em segundo plano

O mesmo service, três portas

src/tasks/ · controller, gateway e processorTS
// Porta REST: POST /tasks
@Controller('tasks')
export class TasksController {
  constructor(private readonly tasks: TasksService) {}

  @Post()
  create(@Body() dto: CreateTaskDto) {
    return this.tasks.create(dto);
  }
}

// Porta WebSocket: evento 'task:create'
@WebSocketGateway()
export class TasksGateway {
  constructor(private readonly tasks: TasksService) {}

  @SubscribeMessage('task:create')
  create(@MessageBody() dto: CreateTaskDto) {
    return this.tasks.create(dto);
  }
}

// Porta fila: um worker pega jobs da fila 'ai' no Redis
@Processor('ai')
export class AiProcessor extends WorkerHost {
  constructor(private readonly tasks: TasksService) { super(); }

  async process(job: Job<{ taskId: string }>) {
    return this.tasks.summarize(job.data.taskId);
  }
}

Os três recebem o mesmo TasksService por injeção. Por isso a regra "lógica no service, não no controller" importa tanto: se a lógica estivesse no controller, você teria que copiá-la para o gateway e para o worker.

Como um projeto profissional se organiza

apps/api/src/ · uma pasta por assunto
src/
├─ main.ts            // sobe a API
├─ app.module.ts
├─ prisma/            // acesso ao banco
├─ auth/              // login, JWT, guards
├─ users/
├─ tasks/
│  ├─ tasks.module.ts
│  ├─ tasks.controller.ts
│  ├─ tasks.service.ts
│  ├─ tasks.service.spec.ts  // testes
│  └─ dto/
│     ├─ create-task.dto.ts
│     └─ update-task.dto.ts
└─ common/            // filtros, interceptors

Por que assim

  • Pasta por assunto (feature), não por tipo. Tudo de tarefas mora em tasks/.
  • Um time pode mexer em tasks/ sem quebrar users/.
  • O comando nest g resource tasks já gera essa estrutura.
  • Se um dia tasks/ virar um microsserviço, ele já está isolado.

O que toda API REST profissional tem

Antes de chegar no controller, o pedido passa por camadas que o Nest já traz prontas. Elas ficam fora do controller para não repetir código em cada rota.

OrdemPeçaFaz o quêUso típico
1MiddlewareMexe no pedido cru, antes de tudoLogs de acesso, CORS, helmet
2GuardDecide se o pedido pode passar"Tem token JWT válido?" "É admin?"
3InterceptorEnvolve a chamada: roda antes e depoisMedir tempo, padronizar a resposta, cache
4PipeValida e converte os dados que chegaramValidationPipe + DTO com class-validator
5Controller → ServiceA rota e a regra de negócioCriar a tarefa no banco
se der erroException filterTransforma o erro numa resposta HTTP padronizada404, 400 com mensagem clara, sem vazar detalhes

Além disso, quase todo projeto sério inclui:

  • DTOs validados: classes que descrevem o formato do corpo do pedido. Dado fora do formato é recusado com 400 antes de chegar no service.
  • Documentação Swagger (@nestjs/swagger): uma página em /docs que lista e testa todas as rotas, gerada a partir do código.
  • Autenticação: login que devolve um JWT e um guard que confere o token em cada rota protegida.
  • Configuração por ambiente: .env diferente em dev, staging e produção, lido pelo ConfigService.
  • Health check (@nestjs/terminus): uma rota como /health que o servidor consulta para saber se a API e o banco estão de pé.
  • Testes: unitários nos services (trocando o banco por um falso) e testes e2e que chamam as rotas de verdade.

Arquitetura comum no mercado: uma API REST para o front-end e um ou mais workers lendo filas no Redis para o trabalho pesado. Tudo no mesmo repositório, compartilhando os mesmos services. É um caminho natural para o FlowMind: a API responde rápido e as chamadas de IA rodam em segundo plano.

Teste seu entendimento

1. Quem é o controller, o service e o module no restaurante?

Garçom, cozinheiro e praça da cozinha.

2. O que acontece com constructor(private prisma: PrismaService)?

O Nest entrega a instância única do PrismaService, já conectada ao banco.

3. Por que o PrismaModule tem @Global()?

Quase todo módulo precisa do banco; assim basta importá-lo uma vez no AppModule.

4. Para que servem onModuleInit e onModuleDestroy?

Conectar ao banco quando a API sobe e fechar as conexões quando ela desliga.

5. NestJS serve só para API REST?

Não. REST é a porta mais comum, mas o mesmo service pode ser chamado por GraphQL, WebSocket, mensagens, filas ou cron. O Nest organiza o backend por dentro.

6. Por que validar o corpo do pedido com DTO + ValidationPipe?

Para recusar dados errados com 400 antes que cheguem no service ou no banco, sem escrever ifs de validação em cada rota.

CRUD REST protegido: o caminho completo de um pedido

A API ganhou rotas para criar, listar, ler, alterar e apagar tarefas (CRUD). Antes de tocar no banco, cada pedido responde três perguntas: quem é você? (Guard), o que você mandou está certo? (Pipe) e essa tarefa é sua? (service). Aulas de apoio: 8 (Validação com DTOs) e 9 (JWT + bcrypt).

Analogia, continuando o restaurante: o segurança da porta (Guard) confere a reserva e a recepcionista (Pipe) confere se o pedido só tem pratos do cardápio, antes do garçom anotar. Onde falha: na API o segurança confere cada pedido de novo, porque HTTP não tem memória.

7. Em que ordem rodam Guard, Pipe e Controller?

Guard → Pipes → Controller: primeiro decide se entra, depois valida, por fim trabalha com dados confiáveis.

8. Por que o DELETE responde 204?

Deu certo e não há nada para devolver: o recurso não existe mais.

9. E se o AuthModule não exportar o AuthGuard?

O TasksModule não consegue usá-lo e a API não sobe: Nest can't resolve dependencies of the AuthGuard (?).
