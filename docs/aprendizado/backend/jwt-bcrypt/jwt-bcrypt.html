Autenticação com JWT e bcrypt

Como o FlowMind guarda senhas sem nunca conhecê-las, entrega um crachá digital no login e confere esse crachá em cada pedido às rotas de tarefas.

Antes de começar

  • Aulas 6, 7 e 8: NestJS, Prisma e validação com DTOs.
  • Cabeçalho HTTP: etiqueta Nome: valor que acompanha o pedido, como Content-Type: application/json. Aqui usamos Authorization.
  • HTTP não tem memória: cada pedido chega sozinho. O cliente precisa provar quem é em todos eles.

O problema e a ideia

O problema, em duas metades

Senhas guardadas e pedidos sem memória

  • Se a tabela users guardar a senha pura e o banco vazar, todas as contas caem, inclusive em outros sites.
  • Depois do login, como provar quem é em cada pedido sem mandar a senha toda vez?

bcrypt guarda só uma impressão digital irreversível da senha. JWT é um crachá assinado que o cliente mostra em cada pedido; o AuthGuard confere.

Analogia

A portaria do prédio

  • Cadastro: o porteiro anota só a impressão digital da sua senha (bcrypt).
  • Login: ele confere a digital e entrega um crachá com holograma: "Ana, válido até 16h" (JWT).
  • Cada porta: um segurança (AuthGuard) olha o holograma (assinatura) e o horário (exp).

Onde a analogia falha: um crachá real dá para recolher na saída. Um JWT vale até expirar, mesmo após "sair". Por isso a validade é curta: 1 hora.

O holograma

  parte1 + "." + parte2,

Mudou uma letra do payload? A assinatura não bate → 401.

Base64URL não é criptografia. Qualquer pessoa decodifica o payload. Nunca coloque senha ou dado sensível nele; guardamos só o id (sub) e o e-mail.

O código, comentado

src/auth/auth.service.ts · loginTS
const user = await this.prisma.user.findUnique({
  where: { email: dto.email },
});
// e-mail inexistente? compara com hash falso
// para gastar o mesmo tempo (timing attack)
const passwordOk = await bcrypt.compare(
  dto.password,
  user?.passwordHash ?? DUMMY_HASH,
);
// mesma mensagem nos dois casos
if (!user || !passwordOk) {
  throw new UnauthorizedException('Credenciais inválidas');
}
return this.buildResponse(user); // sem passwordHash
src/auth/auth.guard.tsTS
const [type, token] =
  request.headers.authorization?.split(' ') ?? [];
if (type !== 'Bearer' || !token)
  throw new UnauthorizedException('Token de acesso ausente');
try {
  // confere assinatura (JWT_SECRET) e exp
  const payload = await this.jwt.verifyAsync(token);
  request.user = { id: payload.sub, email: payload.email };
} catch {
  throw new UnauthorizedException('Token inválido ou expirado');
}
return true; // pode entrar
src/auth/auth.module.tsTS
JwtModule.registerAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    secret: config.getOrThrow('JWT_SECRET'),
    signOptions: { expiresIn: 3600 }, // JWT_EXPIRES_IN
  }),
}),
// ...
exports: [AuthGuard, JwtModule], // p/ o TasksModule
src/tasks/tasks.controller.tsTS
@Controller('tasks')
@UseGuards(AuthGuard)  // todas as rotas exigem token
export class TasksController {
  @Get()
  findAll(@CurrentUser() user: AuthUser) {
    // user = { id, email } vindo do token
    return this.tasksService.findAll(user.id);
  }
}

Glossário

Autenticação
Descobrir quem está fazendo o pedido.
Autorização
Decidir o que essa pessoa pode fazer.
Hash
Embaralhamento irreversível: mesma entrada, mesmo resultado; sem caminho de volta.
bcrypt
Hash para senhas: lento de propósito e com sal embutido.
Sal (salt)
Pedaço aleatório misturado à senha; senhas iguais geram hashes diferentes.
Custo
Quantas rodadas o bcrypt faz (10 = 210).
JWT
Token cabeçalho.payload.assinatura que prova quem é o usuário.
Payload
Os dados do token: sub, email, iat, exp.
Assinatura
Código feito com o payload + segredo; detecta qualquer alteração.
JWT_SECRET
Segredo que só a API conhece, guardado no .env.
Bearer token
Envio padrão: Authorization: Bearer <token>.
Guard
Peça do Nest que decide se o pedido entra, antes do controller.
@CurrentUser()
Decorator nosso que entrega request.user ao controller.
Timing attack
Descobrir informações medindo o tempo de resposta.

Experimente você mesmo

  1. Registre dois usuários

    curl -s -X POST localhost:3000/auth/register -H "Content-Type: application/json" \
  -d '{"email":"exp-a@flowmind.dev","name":"A","password":"senha-forte-123"}'
# repita com exp-b@flowmind.dev

    Esperado: 201 duas vezes. Guarde os dois accessToken.

  2. Crie uma tarefa com o token de A

    curl -s -X POST localhost:3000/tasks -H "Content-Type: application/json" \
  -H "Authorization: Bearer TOKEN_A" -d '{"title":"Segredo da A"}'

    Esperado: 201. Guarde o id.

  3. Tente ler com o token de B

    curl -s localhost:3000/tasks/ID_DA_TAREFA -H "Authorization: Bearer TOKEN_B"

    Esperado: 404 Tarefa não encontrada. B nem fica sabendo que a tarefa existe.

  4. Leia o payload do token de A

    node -e "console.log(JSON.parse(Buffer.from(process.argv[1].split('.')[1],'base64url')))" TOKEN_A

    Esperado: { sub, email, iat, exp }, legível sem segredo nenhum.

  5. Falsifique uma letra

    Troque um caractere no meio do token de A e chame GET /tasks com ele.

    Esperado: 401 Token inválido ou expirado.

  6. Desfaça

    No Prisma Studio, apague exp-a e exp-b. As tarefas vão junto (onDelete: Cascade).

Teste seu entendimento

1. Por que guardar o hash e por que o bcrypt é lento de propósito?

Se o banco vazar, não há senhas, só impressões irreversíveis. A lentidão é imperceptível num login, mas inviabiliza testar milhões de senhas.

2. O payload é secreto? O que impede trocar o sub?

Não é secreto. A assinatura, feita com o JWT_SECRET, deixa de bater se o payload mudar, e o verifyAsync recusa.

3. Autenticação × autorização no CRUD de tarefas?

Autenticação: o AuthGuard descobre quem é. Autorização: o TasksService filtra por userId.

4. Para que serve o DUMMY_HASH?

Para o login com e-mail inexistente demorar o mesmo que uma senha errada. Junto com a mensagem igual, impede descobrir quem tem conta.

5. Por que validade de 1 hora?

Um JWT não pode ser cancelado antes de expirar sem infraestrutura extra. Validade curta limita o estrago se ele vazar.
