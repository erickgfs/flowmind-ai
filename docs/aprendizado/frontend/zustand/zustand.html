O problema e a ideia

O problema

O recado de mão em mão

  • Barra lateral, guarda de rota, cliente da API e botão Sair precisam da sessão.
  • Com useState, o dado é repassado por props por quem nem usa (prop drilling).
  • F5 apaga o estado do React: logout a cada recarga.

O Zustand cria uma store fora dos componentes; o persist a grava no localStorage.

Analogia

O quadro de avisos

  • Store = quadro na parede: quem precisa olha direto nele.
  • Seletor = cada pessoa olha só a linha que interessa.
  • persist = foto do quadro no fim do expediente, usada para remontá-lo no dia seguinte (F5).

Onde falha: o quadro do escritório fica num lugar seguro. O localStorage é legível por qualquer script da página: com XSS, o token pode ser roubado.

Quem lê a store, e o caminho do 401

O código, comentado

stores/auth-store.tsTS
export const useAuthStore = create<AuthState>()(
  persist(
    (set) => ({
      token: null,
      user: null,
      setSession: (token, user) => set({ token, user }),
      logout: () => set({ token: null, user: null }),
    }),
    {
      name: "flowmind-auth",  // chave no localStorage
      storage: createJSONStorage(() => localStorage),
      partialize: (s) => ({ token: s.token, user: s.user }),
    },
  ),
);
uso · componentes e lib/api.tsTS
// ✅ seletor: re-renderiza só se o user mudar
const user = useAuthStore((s) => s.user);

// ⚠️ store inteira: re-renderiza por qualquer mudança
const tudo = useAuthStore();

// fora do React (lib/api.ts)
const token = useAuthStore.getState().token;
if (response.status === 401)
  useAuthStore.getState().logout();

O dilema: localStorage × cookie httpOnly

localStorage + Zustand (o nosso)Cookie httpOnly

Se houver XSStoken pode ser roubadoscript age na página, mas não leva o token

Decisão do projeto: localStorage nesta fase de estudo, token de 1 hora; migração para cookie httpOnly registrada como melhoria futura.

Glossário

Estado global
Dado compartilhado por vários componentes.
Prop drilling
Repassar props por vários níveis só para chegar lá embaixo.
Store
Objeto com o estado e as ações que o mudam.
Seletor
(s) => s.user: escolhe um pedaço do estado.
getState()
Lê a store fora de componentes.
persist
Middleware que salva e recarrega a store.
partialize
Escolhe quais campos salvar.
XSS
Script malicioso rodando dentro do seu site.
Cookie httpOnly
Cookie que o JavaScript da página não consegue ler.

Experimente no navegador

  1. Veja a foto do quadro

    F12 → Application → Local Storage → flowmind-auth.

    Esperado: {"state":{"token":"eyJ…","user":{…}},"version":0}

  2. Troque o nome pelo console

    const s = JSON.parse(localStorage.getItem("flowmind-auth"));
s.state.user.name = "Nome Trocado";
localStorage.setItem("flowmind-auth", JSON.stringify(s));
location.reload();

    Esperado: barra lateral com "Nome Trocado" e "NT". O front confia no que está guardado: permissão nunca se decide no front.

  3. Estrague o token

    Repita com s.state.token = "invalido".

    Esperado: 401 → logout() → /login.

  4. Clique em Sair

    Esperado: "token":null,"user":null na chave.

Teste seu entendimento

1. Store, seletor e persist na analogia?

Quadro de avisos, a linha que cada um lê, a foto do quadro para remontá-lo no dia seguinte.

2. Como lib/api.ts lê o token?

useAuthStore.getState().token: a store existe fora do React.

3. O que acontece num 401?

logout() → token null → AuthGate redesenha → /login.

4. Risco do localStorage?

Qualquer script da página lê o token; com XSS, ele pode ser roubado.

5. Por que as tarefas ficam em useState?

Só o quadro as usa e elas vêm da API; global é só o compartilhado.
