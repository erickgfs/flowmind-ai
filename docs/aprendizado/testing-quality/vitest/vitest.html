O problema e a ideia

O problema

Testar na mão, toda vez

  • Subir Docker, subir API, mandar curl com senha certa, senha errada, e-mail inexistente...
  • Repetir a cada mudança. Um dia você esquece um caso e o login passa a aceitar qualquer senha.

Um teste automatizado usa o seu código e confere o resultado. O Vitest roda todos os *.spec.ts e mostra ✓ ou ✗. O unitário isola uma peça e troca as dependências por dublês.

Analogia

A bancada do mecânico

  • O motor (AuthService) vai para a bancada (Test.createTestingModule), fora do carro.
  • No lugar do tanque, uma mangueira de teste que o mecânico controla (o mock do Prisma).
  • Medidores (expect) conferem cada comportamento.

Onde a analogia falha: a bancada não prova que o motor funciona dentro do carro. O unitário não prova que o Prisma grava no Postgres; isso é papel do teste e2e.

O código, comentado

auth.service.spec.ts · a bancadaTS
const prismaMock = {
  user: { findUnique: vi.fn(), create: vi.fn() },
};
const jwtMock = {
  signAsync: vi.fn().mockResolvedValue('token-falso'),
};

beforeEach(async () => {
  vi.clearAllMocks(); // isola um teste do outro
  jwtMock.signAsync.mockResolvedValue('token-falso');
  const moduleRef = await Test.createTestingModule({
    providers: [
      AuthService, // real
      { provide: PrismaService, useValue: prismaMock },
      { provide: JwtService, useValue: jwtMock },
    ],
  }).compile();
  service = moduleRef.get(AuthService);
});
auth.service.spec.ts · um casoTS
it('lança 401 com senha errada', async () => {
  // Arrange: o "banco" diz que o usuário existe
  prismaMock.user.findUnique
    .mockResolvedValue(storedUser);

  // Act + Assert: deve REJEITAR com 401
  await expect(
    service.login({
      email: storedUser.email,
      password: 'senha-errada',
    }),
  ).rejects.toBeInstanceOf(UnauthorizedException);

  // Assert extra: nenhum token gerado
  expect(jwtMock.signAsync).not.toHaveBeenCalled();
});

Sem o await, o teste mente. expect(promise).rejects sem await termina antes de conferir e passa sempre, mesmo com bug.

Jest × Vitest: o que muda de verdade

A pergunta

"Se eu aprender um, sei o outro?"

Os conceitos, sim (cerca de 90%). Teste unitário, dublês, isolamento, Arrange → Act → Assert, describe/it/expect e todos os matchers são iguais.

O que muda é a instalação: como cada um lê o código, como se configura e como se faz mock de módulo inteiro. É aí que um exemplo copiado da internet quebra.

Analogia

Dois carros de marcas diferentes

Volante, pedais e regras de trânsito são os mesmos. Mas o câmbio, o freio de mão e os botões do painel ficam em lugares diferentes, e no começo você procura o pisca no lugar errado.

Onde a analogia falha: no carro você percebe na hora que errou o botão. No teste, algumas diferenças não dão erro: o teste fica verde sem ter conferido nada.

Error: done() callback is deprecated, use promise instead

Saída real do projeto: o teste aparece como aprovado e o único sinal é o Errors 1 error no rodapé. Nunca ignore esse contador.

Experimente: mockar demais faz o teste mentir

  1. Mocke o bcrypt sem default

    No topo de src/auth/auth.service.spec.ts, abaixo dos imports:

    vi.mock('bcrypt', () => ({ hash: vi.fn(), compare: vi.fn() }));

    Esperado: No "default" export is defined on the "bcrypt" mock

  2. Corrija com a chave default

    vi.mock('bcrypt', () => ({
  default: {
    hash: vi.fn().mockResolvedValue('hash-falso'),
    compare: vi.fn().mockResolvedValue(true), // toda senha "confere"
  },
}));

    Esperado: Tests 1 failed | 4 passed (5), com ✗ em "senha errada".

  3. Leia o resultado

    O teste de registro continua verde, mas não prova nada: o hash salvo é 'hash-falso'. O de senha errada quebrou, porque o compare falso aceita tudo. Ao mockar o assunto do teste, o teste deixa de medir o que importa.

  4. Desfaça

    Apague o vi.mock(...) e rode npm test.

    Esperado: Tests 6 passed (6)

Teste seu entendimento

1. Na bancada, o que são motor, mangueira e medidores?

AuthService, os mocks do Prisma e do JWT, e os expect.

2. Por que o unitário não substitui o e2e?

Ele prova a lógica da peça isolada, mas não que o Prisma grava no Postgres nem que a rota HTTP está ligada.

3. O que { provide: PrismaService, useValue: prismaMock } faz?

Diz ao Nest: quando alguém pedir PrismaService, entregue o objeto falso. Funciona graças à injeção de dependências.

4. Por que o bcrypt ficou real?

O objetivo é provar que a senha vira hash e que o hash confere. Mockar o bcrypt apagaria essa garantia.

5. Como converter este teste para Jest?

Trocar vi. por jest. e configurar o Jest para TypeScript/ESM. O resto é igual.

6. Se você aprende Vitest, sabe Jest?

Os conceitos e a escrita dos testes, sim (cerca de 90%). Mudam a configuração, o jeito de ler o código (CommonJS × ESM) e detalhes do mock de módulos.

7. Por que o vi.mock do bcrypt precisa da chave default?

O Vitest roda ESM, onde o export default é uma gaveta separada. O Jest transforma em CommonJS, onde o módulo é um objeto só.

8. Por que um teste com (done) => … é perigoso no Vitest?

O Vitest não espera o done: o teste termina e passa antes do código assíncrono rodar. Falso positivo; o sinal é o Errors 1 error.

9. Por que mockar o bcrypt inteiro estragou os testes?

O compare falso aceitava qualquer senha e o hash falso salvava sempre o mesmo texto. Mockamos o próprio assunto do teste.
