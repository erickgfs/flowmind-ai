O problema e a ideia

O problema

SQL escondido dentro de textos

db.query("SELECT * FROM taks WHERE user_id = $1", [id])
  • O erro em taks só aparece com o programa rodando.
  • O resultado não tem tipo: o editor não sabe que tarefa tem title.
  • Criar tabelas na mão em cada máquina vira "na minha funciona".

Analogia

A planta do prédio

  • Schema = planta do arquiteto: quais cômodos (tabelas) existem.
  • Migration = ordem de obra datada: "19/10, construir users e tasks". Nada é refeito.
  • Prisma Client = interfone com a lista de moradores: só chama quem existe na planta.

Onde a analogia falha: prédios quase nunca mudam de planta. O schema muda o tempo todo, e cada mudança vira uma nova migration.

prisma/schema.prisma (trecho)Prisma
model Task {
  id     String     @id @default(uuid()) @db.Uuid
  title  String
  description String?          // ? = opcional
  status TaskStatus @default(TODO)
  userId String @map("user_id") @db.Uuid
  user   User   @relation(
    fields: [userId], references: [id],
    onDelete: Cascade)   // não vira coluna

  @@index([userId])
  @@map("tasks")          // nome da tabela
}
migrations/…_init/migration.sqlSQL gerado
CREATE TYPE "TaskStatus" AS ENUM
  ('TODO', 'IN_PROGRESS', 'DONE');

CREATE TABLE "tasks" (
  "id" UUID NOT NULL,
  "description" TEXT,
  "status" "TaskStatus" NOT NULL DEFAULT 'TODO',
  "user_id" UUID NOT NULL,
  CONSTRAINT "tasks_pkey" PRIMARY KEY ("id")
);
CREATE INDEX "tasks_user_id_idx" ON "tasks"("user_id");
ALTER TABLE "tasks" ADD CONSTRAINT "tasks_user_id_fkey"
  FOREIGN KEY ("user_id") REFERENCES "users"("id")
  ON DELETE CASCADE;
prisma.config.tsTS
import 'dotenv/config';   // Prisma 7 não lê .env sozinho

export default defineConfig({

Glossário

ORM
Camada que traduz entre objetos do código e tabelas do banco.
Schema / Model / Campo
O arquivo de planta / um bloco que vira tabela / uma linha que vira coluna.
@ e @@
Atributos de campo (@id, @unique) e de model (@@map, @@index).
Enum
Lista fechada de valores permitidos.
Relação 1:N
Um usuário ligado a várias tarefas.
onDelete: Cascade
Apagar o pai apaga os filhos.
UUID
Identificador aleatório de 36 caracteres, difícil de adivinhar.
Migration
Arquivo SQL datado com uma mudança no banco, guardado no Git.
Prisma Client
Código gerado com métodos tipados para consultar o banco.
Driver adapter
Conecta o Prisma 7 ao banco pelo driver pg.
DATABASE_URL
postgresql://usuario:senha@host:porta/banco
Prisma Studio
Tela no navegador para ver e editar dados.

Experimente você mesmo

Criar um usuário e duas tarefas no Prisma Studio e ver o cascade funcionando. No fim, não sobra nada.

  1. Abra o Studio

    cd apps/api
npm run prisma:studio

    Esperado: abre http://localhost:5555 com User e Task.

  2. Crie um usuário

    email = teste@flowmind.dev, name = Teste, passwordHash = x. Salve.

    Esperado: id, createdAt e updatedAt preenchidos sozinhos.

  3. Crie duas tarefas desse usuário, sem preencher status

    Esperado: status = TODO e priority = MEDIUM.

  4. Repita o e-mail num novo usuário

    Esperado: Unique constraint failed on the fields: (email).

  5. Apague o usuário e abra Task

    Esperado: as duas tarefas sumiram junto. Feche o Studio com Ctrl+C.

Teste seu entendimento

1. Quais são as três peças do Prisma?

Schema (descreve), Migrate (gera e aplica o SQL das mudanças) e Client (consulta com tipos).

2. O campo tasks Task[] do User vira coluna?

Não. É só navegação no Prisma. A coluna real é user_id em tasks.

3. O que acontece com as tarefas ao apagar o usuário?

São apagadas junto, por causa do onDelete: Cascade (ON DELETE CASCADE na FK).

4. Para que servem @map e @@map?

Nomes diferentes no código e no banco: createdAt → created_at, User → users.

5. Por que instalamos @prisma/adapter-pg?

No Prisma 7 a conexão é feita por um driver adapter em JavaScript; para PostgreSQL ele usa o driver pg.
